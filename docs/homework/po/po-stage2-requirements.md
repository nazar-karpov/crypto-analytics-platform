# Задание 2. PO. Магомедов Арсен

## Этап 1. Область, задача, метрики

### Направление

Крипторынок / market intelligence — платформа real-time аналитики
публичных котировок (не трейдинг-бот и не кастодиальный продукт).

**Почему это направление:**
- данные открытые (CoinGecko API) — нет 152-ФЗ и долгого согласования доступов;
- понятная бизнес-ценность: «что происходит с рынком прямо сейчас» и «что было за сутки/неделю»;
- хорошо ложится на стек из Задания 1: S3 (MinIO) + Kafka + ClickHouse + BI/AI.

### Задача (финальный проект)

Собрать MVP Real-time Crypto Analytics Platform:

1. Стримить топ-50 монет с CoinGecko в Kafka.
2. Класть сырьё в STG (Parquet / MinIO), чистить в DDS, считать витрины DDM в ClickHouse.
3. Отдать ценность наружу: дашборд Grafana + AI-агент с SQL к витринам.

**Out of scope на этом этапе**: Iceberg/Delta, прогноз цен, торговые
сигналы, мульти-источники (биржи), RBAC/каталог.

### Метрики успеха MVP

| Тип | Метрика | Целевое значение | Зачем |
|---|---|---|---|
| Продукт | Time-to-dashboard | ≤1 рабочий день после `docker compose up` и прогрева пайплайна | Первые графики без ручной выгрузки |
| Данные | Свежесть STG | Новый Parquet не реже чем раз в несколько минут при работающем producer | Поток живой, не «залили CSV раз» |
| Данные | Покрытие DDM | 4 витрины заполнены: `mart_hourly_ohlcv`, `mart_top_movers`, `mart_market_overview`, `mart_coin_stats` | Закрываем базовые вопросы рынка |
| Надёжность | Идемпотентность `dds_to_ddm` | Повторный прогон DAG не дублирует смысл витрин (ReplacingMergeTree / пересчёт) | Доверие к цифрам |
| UX | AI-агент | ≥3 типовых вопроса дают корректный SQL и ответ из ClickHouse | Self-service без знания схемы |
| Ops | Сложность контура | Весь стек в Docker Compose, без внешнего managed-кластера | Маленькая команда тянет сама |

## Этап 2. Разговор с командой по финальному проекту

**Участники**: PO, Data Engineer, Backend (AI-агент), аналитик/потребитель
дашборда (роль «заказчик внутри»).
**Цель встречи**: зафиксировать scope MVP, слои данных и DoD, чтобы не
расползтись в «настоящий lakehouse».

### Что обсудили

PO предложил рамку: ClickHouse + S3, слои STG → DDS → DDM, Grafana +
агент. Попросил подтвердить, что за 4 спринта это реально, и что именно
считается «готово».

**Data Engineer:**
- согласен со стеком, но против Iceberg и Spark на MVP — иначе съедим все спринты на Ops;
- Kafka оставляем только под сырые цены; consumer пишет partitioned Parquet в `stg/prices/`;
- DDS: SCD2 по монетам + fact цен; оркестрация — Airflow + pandas;
- DDM: четыре витрины в ClickHouse, DAG каждые ~5 минут;
- риск: rate limit CoinGecko и «дыры» в STG — нужны initial load и понятные ретраи Airflow.

**Backend (агент):**
- агент только читает DDM в ClickHouse, не ходит в MinIO и не пишет в озеро;
- tool calling + ограниченный набор таблиц — чтобы модель не фантазировала схему;
- ключ OpenRouter в `.env`, сервис не блокирует пайплайн данных.

**Аналитик / заказчик:**
- на дашборде в приоритете: OHLCV по часу, топ растущих/падающих за 24ч, обзор рынка (капитализация, доминация BTC/ETH), базовая статистика монеты;
- «просто SQL к сырому S3» не подходит — нужна стабильная витрина;
- AI полезен как ускоритель вопросов, но цифры на Grafana — источник правды.

### Что зафиксировали (решения)

| Тема | Решение |
|---|---|
| Продукт | MVP crypto analytics: ingest → lake-файлы → витрины → Grafana + AI |
| Хранение | MinIO: STG + DDS (Parquet); ClickHouse: только DDM |
| Стриминг | Kafka + Python consumer (без Spark) |
| ETL | Airflow: `stg_to_dds`, `dds_to_ddm`, `initial_load` |
| BI / AI | Grafana на витринах; FastAPI-агент только к ClickHouse |
| Не делаем | Iceberg/Delta, Trino поверх S3, ML прогнозов, сложный RBAC |
| DoD | `compose up` → данные в STG/DDS → 4 mart заполнены → дашборд и 3+ рабочих вопроса к агенту |

### Открытые вопросы (на потом)

- Алерты в Grafana при аномальной волатильности.
- Второй источник (биржа) — только после стабилизации CoinGecko-контура.
- Перенос MinIO/CH в managed Yandex Cloud без смены модели слоёв.

## Этап 3. Обратная связь по разговору

**Что сработало:**
- Разговор шёл от ценности (витрины + дашборд), а не от списка технологий — команда быстрее согласилась резать scope.
- Явно назвали анти-цели (Iceberg, Spark, ML) — снизили риск «тихого расползания» архитектуры.
- DoD сформулировали проверяемо: конкретные витрины и сценарии агента, а не «платформа готова».

**Что улучшить в следующий раз:**
- Сразу принести 3–5 примеров вопросов бизнеса («кто в топ-10 за 24ч?», «волатильность BTC за 7д?») — тогда витрины и Grafana собираются от вопросов, а не наоборот.
- Заложить 15 минут на риски данных (rate limit API, пустой STG, отставание DAG) отдельным блоком — на встрече это всплыло в конце и почти ушло «на потом».
- Зафиксировать владельцев (кто отвечает за producer, DAG, дашборд, агента) прямо в протоколе — иначе PO остаётся единственной точкой эскалации по всем слоям.

**Вывод для PO:**
Команда подтвердила финальный проект: тонкий data-контур под
крипто-котировки с витринами в ClickHouse. Следующий шаг — идти по
спринтам из Задания 1 и сверять прогресс только с метриками Этапа 1, не
расширяя scope без новой встречи.

## Требования к Data Platform

### Функциональные требования

| ID | Требование | Описание |
|---|---|---|
| FR-01 | Ingest котировок | Платформа периодически забирает цены топ-50 монет из CoinGecko API. |
| FR-02 | Буферизация потока | Сырые события котировок публикуются в Kafka-топик `raw_crypto_prices`. |
| FR-03 | Сырой слой STG | Consumer пишет события в MinIO как Parquet, партиции по дате/часу (`s3://stg/prices/`). |
| FR-04 | Очищенный слой DDS | ETL строит измерение монет (SCD2) и fact цен в `s3://dds/`. |
| FR-05 | Начальная загрузка | Есть `initial_load` для заполнения истории без ожидания накопления стрима. |
| FR-06 | Витрина OHLCV | DDM отдаёт почасовой OHLCV по монетам (`mart_hourly_ohlcv`). |
| FR-07 | Витрина топ-муверов | DDM отдаёт топ растущих/падающих за 24ч (`mart_top_movers`). |
| FR-08 | Витрина обзора рынка | DDM отдаёт капитализацию, доминацию BTC/ETH, объём (`mart_market_overview`). |
| FR-09 | Витрина статистики монеты | DDM отдаёт avg 7д/30д, волатильность, max drawdown (`mart_coin_stats`). |
| FR-10 | Оркестрация ETL | Airflow запускает `stg_to_dds` и `dds_to_ddm` по расписанию, с зависимостью между DAG. |
| FR-11 | BI-дашборд | Grafana показывает витрины DDM без ручных выгрузок. |
| FR-12 | AI self-service | FastAPI-агент принимает вопрос на естественном языке, строит SQL к DDM и возвращает ответ. |
| FR-13 | Повторный прогон без порчи данных | Повторный `dds_to_ddm` не создаёт ложных дублей смысла витрин (ReplacingMergeTree / идемпотентная запись). |
| FR-14 | Наблюдаемость пайплайна | Статусы DAG, логи producer/consumer и доступ к UI Airflow/MinIO/ClickHouse для диагностики. |

### Нефункциональные требования

| ID | Категория | Требование | Целевой ориентир (MVP) |
|---|---|---|---|
| NFR-01 | Performance | Задержка от тика API до появления в STG | минуты (не субсекунды); producer ~30 сек |
| NFR-02 | Performance | Обновление витрин DDM | цикл ETL ≤5–60 мин (по расписанию DAG) |
| NFR-03 | Availability | Контур поднимается одной командой | `docker compose up -d`, восстановление сервисов после рестарта контейнеров |
| NFR-04 | Security | Секреты не в репозитории | API-ключи (OpenRouter и т.п.) только в `.env`/secrets; дефолтные пароли MinIO/Airflow — только для sandbox |
| NFR-05 | Security | Доступ агента | агент — read-only к ClickHouse DDM; нет записи в MinIO/Kafka из агента |
| NFR-06 | Compliance | Персональные данные | только публичные рыночные котировки; PII не собираем → упрощённый контур без 152-ФЗ на MVP |
| NFR-07 | Cost | Стоимость владения MVP | self-hosted OSS в Docker на 1 машине (8–16 ГБ RAM); без платных PaaS кроме LLM API |
| NFR-08 | Maintainability / Portability | Смена среды без смены модели данных | слои STG/DDS/DDM и схемы `mart_*` переносимы в managed S3 + ClickHouse |

### Песочница vs Production по сценариям использования

| Сценарий использования | Среда | Почему |
|---|---|---|
| Разработка producer/consumer, отладка схемы Parquet | Sandbox | Можно ронять топики/бакеты, синтетические и укороченные прогоны |
| Отладка DAG Airflow (`stg_to_dds`, `dds_to_ddm`) | Sandbox | Частые ручные trigger, допустимы неполные партиции |
| Проверка Grafana-панелей и SQL витрин | Sandbox → smoke в Production | Вёрстка/запросы — в песочнице; финальная сверка на «боевых» витринах |
| Демо курса / защита MVP заказчику | Sandbox (демо-контур) | Docker Compose на локальной/учебной машине = принятый «боевой» контур курса; секреты учебные |
| Ежедневный мониторинг рынка командой (как продукт) | Production | Нужны стабильный ingest 24/7, бэкапы, не-дефолтные пароли, мониторинг |
| AI-агент: промпт-инжиниринг и новые вопросы | Sandbox | Ошибки SQL и расход токенов не должны бить в prod-квоты без контроля |
| AI-агент: ответы для пользователей продукта | Production | Read-only, лимиты, аудит запросов, отдельный API-ключ |
| Initial load / пересчёт истории | Sandbox сначала, затем Production | Логику обкатать на копии; в prod — по окну обслуживания |
| Нагрузочный тест (частота опроса API, объём Parquet) | Sandbox | Чтобы не упереться в rate limit «боевого» ключа/IP и не забить prod-диск |
| Смена паролей, сеть, IAM, TLS, политики доступа | Production | В sandbox достаточно shared credentials; в prod — обязательный hardening |
| Эксперимент с Iceberg / вторым источником (биржа) | Sandbox only (вне MVP) | Не смешивать R&D с витринами, на которых сидит дашборд |
| Инцидент «витрины устарели / DAG упал» | Production runbook + воспроизведение в Sandbox | Чиним по процедуре в prod; корневую причину разбираем на копии |

### Политика сред

| | Sandbox (текущий Docker Compose MVP) | Production (целевое) |
|---|---|---|
| Данные | Публичные котировки, можно очищать бакеты | Та же модель слоёв; ретеншн и бэкапы DDS/DDM |
| Секреты | `.env`, допустимы слабые дефолты для учёбы | Secrets manager, ротация, без паролей из README |
| Доступ | Локальный / учебная сеть | Сеть, TLS, раздельные роли Grafana/CH/Airflow |
| AI | Общий ключ OpenRouter для разработки | Отдельный ключ, rate limit, только read SQL |
| Критерий «можно в prod» | FR-01…FR-14 + NFR-04/05 выполнены на staging-копии | Плюс мониторинг, бэкап, ужесточённый доступ |
