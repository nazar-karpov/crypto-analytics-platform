# Задание 1. PO. Магомедов Арсен

## Сценарий

Мы небольшая продуктовая команда, которая строит платформу аналитики
криптовалют. Источник данных — публичный API CoinGecko (топ-50 монет,
котировки каждые ~30 сек). Нам нужна основа для data-платформы: сырые
цены в объектном хранилище, очищенные слои, витрины для дашбордов и
SQL/AI-запросов. Персональных данных пользователей нет (только рыночные
котировки), поэтому жёсткой привязки к 152-ФЗ нет, но мы всё равно
склоняемся к открытому стеку и минимальному vendor lock-in. Штат маленький
— предпочитаем Buy (managed) там, где это экономит DevOps, либо тонкий
Make на проверенном OSS, без Hadoop «с нуля».

## Итоговое решение и обоснование

1. **Почему не чистый Make на «голом» Hadoop**: наша цель — продукт
   аналитики крипторынка, а не собственная IT-корпорация. Полный Make
   (Hadoop/Kubernetes с нуля) потребует 3–4 инженеров и DevOps. Для MVP
   достаточно тонкого контура: объектное хранилище + оркестратор + OLAP.

2. **Почему ориентир — РФ-стек / OSS, а не Snowflake/Databricks**:
   персональных данных игроков у нас нет, но важны стоимость, скорость
   выхода на дашборд и отсутствие жёсткого lock-in. Западные PaaS дают
   Time-to-dashboard, но дороже на потоке котировок и сильнее привязывают
   к вендору. Нам нужен открытый контур, который можно поднять локально
   (Docker Compose) и при росте перенести в managed-облако без смены
   модели данных.

3. **Победитель рейтинга: Yandex-паттерн (ClickHouse + S3)** — по
   Battle-card выбираем архитектуру «озеро в S3 + витрины в ClickHouse»
   (как у Yandex Cloud / self-hosted MinIO + ClickHouse).

### Аргументация по метрикам

- **Storage Efficiency: 4/5** — исторические Parquet-котировки лежат
  дёшево в Object Storage (S3/MinIO). Сырьё и очищенные слои не раздувают
  дорогие диски OLAP.
- **Crypto streaming: 5/5** — котировки идут часто. ClickHouse хорошо
  принимает частые вставки в витрины; буфер событий — Kafka.
- **Time-to-dashboard / Self-service: 4–5/5** — витрины `mart_*` +
  Grafana дают графики за часы, не недели. SQL к ClickHouse понятен
  аналитикам; поверх — AI-агент с tool calling.
- **Vendor Lock-in: 5/5** — Parquet в S3 + ClickHouse Open Source. При
  необходимости меняем только managed-оболочку, не модель данных.
- **ML / AI: 3/5 (достаточно для фазы 1)** — полноценный Jupyter Hub не
  нужен сразу. Достаточно FastAPI-агента, который генерирует SQL к
  витринам.

## Встреча с Архитектором

**Что утвердили:**

- Не делаем «настоящий» Lakehouse на Iceberg/Delta. Оставляем plain
  Parquet в MinIO (STG/DDS) и OLAP-витрины в ClickHouse (DDM). Это
  быстрее для учебного/MVP-контура.
- Kafka оставляем, но узко: только поток сырых цен CoinGecko →
  `raw_crypto_prices` → consumer пишет STG. Не тащим весь «enterprise
  streaming».
- Spark убираем: consumer и ETL на Python + pandas + Airflow. Меньше Ops.
- BI: Grafana (не Superset). AI: отдельный сервис к ClickHouse, без
  Jupyter Hub.
- Слои: STG → DDS (SCD2 + fact) → DDM (`mart_hourly_ohlcv`,
  `mart_top_movers`, `mart_market_overview`, `mart_coin_stats`).

## План на 4 спринта

**Sprint 1: Foundation (фундамент и сырьё)**
Задача: поднять Docker-контур (Kafka, MinIO, ClickHouse, Airflow),
producer CoinGecko → Kafka → Parquet в `s3://stg/prices/`.
Бизнес-ценность: единая точка сырых котировок.

**Sprint 2: DDS (очистка и модель)**
Задача: DAG `stg_to_dds` — измерение монет (SCD2) + fact цен в `s3://dds/`.
Бизнес-ценность: воспроизводимая «чистая» история для витрин.

**Sprint 3: DDM + BI (витрины и дашборд)**
Задача: DAG `dds_to_ddm` → таблицы `crypto.mart_*` в ClickHouse; дашборд
Grafana.
Бизнес-ценность: OHLCV, топ-муверы, обзор рынка и статистика монет без
ручных выгрузок.

**Sprint 4: AI-агент + Data Quality / Документация**
Задача: FastAPI-агент (OpenRouter) с SQL к витринам; базовые проверки
идемпотентности (ReplacingMergeTree); README/документация пайплайна.
Бизнес-ценность: вопросы к рынку на естественном языке + доверие к
цифрам.

## Что не войдёт в спринты

- **Полноценный Lakehouse (Iceberg / Delta / Hudi + каталог)**. Причина:
  на 4 спринта и малый штат не тянем табличный формат, metastore и
  движок SQL поверх озера. MinIO остаётся файловым data lake, семантика
  склада — в ClickHouse.
- **Управляемый облачный PaaS (VK / Yandex managed «под ключ»)**.
  Причина: для MVP достаточно self-hosted Docker Compose с тем же
  паттерном (S3 + ClickHouse). Managed — следующий этап при росте
  нагрузки.
- **Тяжёлый ML (прогноз цен, feature store, GPU)**. Причина: сейчас
  ценность — витрины + дашборд + SQL/AI-агент. Обучение моделей —
  отдельная фаза.
- **Сложный RBAC и Data Catalog / Lineage**. Причина: команда маленькая,
  один контур. Документация в репозитории; единый доступ к
  ClickHouse/Grafana.

## Ретроспектива: анализ и согласование

**Что пошло не так?**
В первой версии Battle-card заложили «настоящий» lakehouse (Iceberg +
Kafka everywhere + Jupyter). Архитектор указал, что для малого контура
это неподъёмно. Пришлось явно развести: озеро файлов (Parquet) vs
витрины (ClickHouse) и не называть Iceberg обязательным.
Ожидание «Buy за неделю» vs реальность: даже на Yandex-паттерне
self-hosted связка Kafka → MinIO → Airflow → ClickHouse требует отладки
оркестрации и схем витрин. Time-to-dashboard оказался ближе к дням, не к
часам.

**Что получилось?**
Стек совпал с победителем Battle-card: ClickHouse + S3 (MinIO) — дешёвая
история котировок и быстрые OLAP-витрины. Прозрачная цепочка ценности:
Ingest (Kafka) → STG/DDS (MinIO + Airflow/pandas) → DDM (ClickHouse) →
Grafana / AI-агент. Отказ от Spark упростил Ops и ускорил доставку
DAG'ов `stg_to_dds`/`dds_to_ddm`.

**Что бы сделали иначе?**
Сначала контракт данных, потом выбор облака: начать с вопроса «как тик
CoinGecko попадает в витрину OHLCV?» и только потом сравнивать PaaS.
Иначе легко купить платформу с Iceberg/Jupyter, которая не нужна в
фазе 1. Ранее зафиксировать, что DDM живёт в ClickHouse, а не «SQL прямо
по сырому S3»: это снимает ложные ожидания lakehouse и экономит 1–2
спринта на каталогах и Trino.
