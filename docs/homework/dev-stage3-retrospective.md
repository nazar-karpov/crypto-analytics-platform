# Домашнее задание — Разработчик, Занятие 2
## Этап 3: Согласование и ретроспектива

## Что получается

- Полный медальон STG→DDS→DDM работает end-to-end, DDS — настоящий
  Iceberg lakehouse, а не просто Parquet под другим именем
- Все FR PO покрыты, кроме FR-12 (см. ниже) — включая усиленную
  идемпотентность (FR-13) и наблюдаемость (FR-14)
- ACID, time travel, schema evolution, мульти-движковый доступ (pandas +
  DuckDB) — продемонстрированы тестами, не только продекларированы
- Persistence каталога через рестарт контейнера — проверено, не
  предположение
- SCD2 корректно работает на реальных данных (переименование монеты,
  новая монета, идемпотентный повтор без дублей)

## Что не получается / открытые вопросы

- **FR-12 (AI-агент)** — не реализован в этой итерации; DoD скорректирован
  соответственно (см. [Этап 1](dev-stage1-pipeline.md))
- **NFR-07 (память)** — полный стек из ~15 сервисов не прогонялся
  одновременно за один заход в этой сессии; тестировалось изолированными
  подмножествами, чтобы не упереться в OOM на разработческой машине.
  **Перед самой защитой стоит один раз поднять `docker compose up -d`
  целиком на машине, с которой будет демо**, и убедиться, что укладывается
  в её RAM — единственный пункт, проверенный только частично.
- **Healthcheck `iceberg-rest`** — заведён через `bash /dev/tcp`-пробу, а
  не через штатный HTTP-эндпоинт (образ каталога не содержит
  `curl`/`wget`) — рабочее решение, но не самое «чистое».
- **`iceberg-rest` запущен под `root`** — сделано, чтобы процесс мог
  писать persistent SQLite-каталог на volume; приемлемо для
  локального/учебного контура, не паттерн для продакшна — осознанное
  ограничение, не недосмотр.

## Вывод

Проект готов к защите как конвертация DDS в Apache Iceberg lakehouse
поверх уже согласованного с PO контура (Kafka/MinIO/Airflow/ClickHouse/
Grafana). Единственное, что стоит сделать до самой защиты — контрольный
прогон полного `docker compose up -d` на демо-машине (см. NFR-07 выше).
